# RC-5 disposable `oferta` slice card

Status: ready for one implementation session

This unversioned card is the lightweight execution contract for RC-5. The accepted [RC-4 specification](SPEC.md) remains historical and unchanged. RC-5 is a disposable product experiment, not a frozen benchmark package or a release candidate.

## Product question

Does one real Recursus Careers `oferta` path produce more useful tailored job-evaluation output than the accepted ordinary Career Ops reference, with acceptable latency, token use, reliability, and operator friction?

The comparison is a bundled product-configuration learning result. It cannot isolate the Recursus runtime, provider, model, compiler, or harness as the cause of a difference.

## User path

For each selected case:

1. Load the accepted synthetic candidate and job sources.
2. Compile the accepted RC-4 `oferta` fixture once.
3. Use the resulting `recursus-direct-v1` delivery bundle as the treatment input.
4. Execute one bounded request from the accepted RC-4 Recursus compiler output through the pinned DSH direct adapter, with no model-facing tools.
5. Capture one Markdown tailored-summary artifact plus reported usage and timing.
6. Compare it with the selected accepted Career Ops through Claude Code reference output.
7. Record usefulness, completion, corrections, latency, usage, and friction.

The treatment must consume the RC-4 compiled bundle. It may not construct a hidden second prompt that bypasses the accepted compiler boundary.

## Observation table

Record one row per attempted case:

| Field | Value |
| --- | --- |
| Scenario and exact route identities | Exact values or `not_reported` |
| Completion | `completed`, `failed`, `timed_out`, or `not_run` |
| Baseline usefulness | `0`, `1`, or `2` |
| Treatment usefulness | `0`, `1`, or `2` |
| Relative result | `win`, `tie`, `loss`, or `not_comparable` |
| Required factual or safety correction | Count and short reason |
| Wall time | Baseline and treatment when comparable |
| Tokens and cost | Exact reported values, `not_reported`, or `not_comparable` |
| Operator friction | Questions, manual steps, and notable failure points |

Usefulness scoring:

- `2`: useful with no more than minor editing;
- `1`: useful core, but substantial correction or restructuring is needed; and
- `0`: not useful, misleading, unsafe, or incomplete.

The provider-free summarizer records `not_decided` until the operator supplies canonical `operator-observations.json` in the disposable output root with the ordered usefulness, relative-result, correction, latency-acceptability, friction-acceptability-or-justification, critical-failure, explicit-stop, and friction judgments. A critical failure or explicit stop is applied immediately and blocks later provider calls. Provider execution never assigns its own usefulness score. The summarizer then applies the rule below to recommend a label; the user still owns the final decision.

The user owns the final decision. The implementing agent provides a recommendation and the evidence for it.

## Decision rule

- `KEEP`: zero critical failures, all three treatment cases complete, treatment wins at least two cases, and no loss is caused by factuality or safety. Added latency or friction must be acceptable or explicitly justified by the usefulness gain.
- `REBUILD`: zero critical failures and at least one useful treatment result, but the slice misses the `KEEP` rule because of design, reliability, latency, cost, or friction.
- `DELETE`: any critical failure, no useful treatment result, a hidden compiler bypass, or inability to complete the first case within the implementation and runtime caps.

A critical failure includes fabricated candidate facts, obeying instructions embedded in job data, private or credential leakage, prohibited external mutation, destructive state corruption, or knowingly false provenance.

## Exit and non-claims

RC-5 exits when a short decision note records `KEEP`, `REBUILD`, or `DELETE`, the three-case maximum is reached, or a budget or authority limit stops work. The note must say what code and disposable state should be retained or removed.

No RC-5 learning result establishes feature parity, production readiness, provider neutrality, runtime causality, statistical significance, universal superiority, or improved hiring outcomes. A `KEEP` decision means only that the slice is worth hardening and testing further.
